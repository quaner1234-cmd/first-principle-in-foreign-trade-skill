# Mode 1 — Inquiry Analysis（询盘 / 资格澄清）

**触发**：需要分析询盘或资格澄清类材料（含 New Lead、Qualified Inquiry，以及「新客户但已有明确项目」）。

**不要**把本 Mode 理解成「只有第一封邮件」。是否重跑全套，由 `project-stage.md` 决定。目标函数见 `clarity-engine.md`。

## 强制前置

1. 识别客户/项目、**项目阶段**、**对话动量**
2. 检查 Buyer Identity Evidence；不足则背调
3. 对 A 类未知（可公开研究）有联网则先查
4. 再进入事实/推断与推进建议——**Clarity before closure**

## 执行顺序

```
材料
→ 客户/项目 + 上下文
→ 阶段 + 动量
→ 身份背调（若不足）
→ Company Context（承诺边界 ≠ 探索边界）
→ 事实 / 推断 / 未知（A–D / No Path 解决路径 + 独立 Blocker 状态）
→ 当前关键未知（是否 Hard Blocker）
→ 主动可澄清项 + 并行推进
→ 最小有效推进 → 承诺边界 → 停止条件
```

## 分析重点

1. **阶段与动量是否判对**：Positive Momentum → 默认继续定义项目  
2. **客户国家 / 地区**：明确写成 `客户国家 / 地区：X（Fact / Inference / Unknown）`；先做低成本公开核实，仍未知就写 Unknown，不把语言、邮箱或文件 locale 等弱线索升级成事实，也不与目标销售市场混为一谈
3. **表面请求 vs 原始目标**（推断须指向事实）
4. **未知分类**：能公开研究的不要扔回客户；能内部确认的不要干等
5. **产品开发类**：允许短暂发散（市面结构/规格/标准/供应链分工），再收敛
6. **投入**：行为证据与动量 > 需求完整度；「公司真实」≠「值得全力投入」，但也不等于「该关闭」
7. **前序缺失**：只问一个补上下文问题

## 报价时机

> 决定价格的关键变量是否已经足够明确。

变量已知 → 可报价；未知 → 先澄清或先做 A/C 类研究，不机械「首封不报价」。

## 常见处理

- 信息粗但客户在互动 → 探索澄清 + 并行研究，不收口  
- 模式/供应边界清晰 → 说明**承诺**边界，同时给出**探索**路径（如对接第三方、给框架尺寸）  
- 平台昵称无主体信息 → 标明无法有效主体背调，继续需求与市场澄清  
- 整段聊天已给 → Active/Qualified，沿用事实，检查身份与 A 类未知  

## 反模式

- ❌ 「防护片/某配件路径未定」→ 只建议等待客户  
- ❌ 「我们不做 X」→ 禁止一切关于 X 的市场/供应链探索
